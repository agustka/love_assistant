# Test Conventions

## Directory Structure

| Directory | Purpose | Test function |
|-----------|---------|---------------|
| `test/user_acceptance_tests/` | Feature acceptance tests | `testWidgets()` |
| `test/domain/` | Value object and entity business-logic tests | `test()` |
| `test/presentation/` | Golden visual regression | `testGoldens()` |
| `test/_core/` | Shared test infrastructure (builders, drivers, test rig) | — |

## Allowed test types (strict)

- Only these test types may be generated by agents:
  - value object tests under `test/domain/<feature>/value_objects/`
  - entity tests under `test/domain/<feature>/entities/` **only when entity business logic/computed behavior is added**
  - golden tests under `test/presentation/<feature>/`
  - user acceptance tests under `test/user_acceptance_tests/<feature>/`

## Forbidden test types

- Do not create use-case tests (for example `test/domain/**/use_cases/*_test.dart`).
- Hard failure: generation of any new test under `test/domain/**/use_cases/` must fail the testing run and be reported as a policy violation.
- Do not create application-layer tests under `test/application/**`.
- Do not create infrastructure-layer tests under `test/infrastructure/**`.

## UAT Tests (`test/user_acceptance_tests/`)

- Use the **driver–builder** pattern. Tests read like plain English; all finders, assertions, and interactions live in the driver.
- Structure each `testWidgets` body with `// Given`, `// When`, `// Then` comments.
- Name tests as descriptive scenario labels (e.g. `"Biometrics enrollment step displayed"`), not `"should …"` sentences.
- Keep `testWidgets` titles concise while preserving AC intent; avoid copying long AC text verbatim.
- Prefer title length that keeps `testWidgets("<title>", (WidgetTester tester) async {` on one line after formatting.
- Every UAT file must call `tearDown(() async { await closeApp(); });` once at the top of `main()`, before any `group()`.
- Drivers extend `BaseDriver`. Feature drivers live at `test/user_acceptance_tests/{feature}/driver/{feature}_driver.dart`.
- The launching page driver (the one that calls `openPage()` first) must be named `driver`.
- Builders are passed only to the launching `driver`; all other drivers must be created without `builders`.
- Declare drivers in this order: `AppDriver` first, then auxiliary feature drivers, and `driver` last.
- Driver methods follow the naming: `openPage()`, `assertXxx()`, `tapXxx()`, `enterXxx()`.
- Test files must not call `tester.*` directly. The only allowed test-file usage of `tester` is passing it into `AppDriver` and feature-driver constructors.
- Test files must not perform low-level widget checks directly (`expect(...)`, `find.*`, widget property reads, or `tester.widget(...)`). Keep these checks in driver or `AppDriver` assertion methods.
- Finders in drivers use `find.byKey()` with static `Key` constants from presentation widgets — never magic strings or `find.text()`.
- Every driver `find.byKey()` lookup must be declared as a finder getter/helper on the driver. Do not write inline `find.byKey(...)` inside assertion or interaction methods.
- Avoid `find.descendant()` in driver assertion and interaction methods — it couples tests to widget tree structure and breaks when the tree changes. Prefer adding a dedicated `Key` to the target widget instead.
- Avoid `find.byType()` — it is not specific enough and may match multiple widgets. Always prefer `find.byKey()` with static `Key` constants from the presentation layer.
- If a widget lacks the needed static `Key`, add one to the presentation widget rather than falling back to `find.byType()` or `find.descendant()`.
- If a scenario appears to need `tester.pumpAndSettle()` or any other raw `tester.*` call, add or reuse a driver/`AppDriver` method instead of writing it in the test file.
- Use `AppDriver(tester: tester)` for cross-cutting concerns (navigation assertions, page existence assertions, dialogs, pop, generic tap).
- Being on a page is always asserted with `AppDriver.assertIsOnPage(PageName.<page>)` or `AppDriver.assertPageExists(PageName.<page>)`.
- Checking that a page is absent is always asserted with `AppDriver.assertPageDoesNotExist(PageName.<page>)`.
- Never add page-level identity `Key` constants or page-presence finders. Page assertions use the route/page descriptor recorded by the app navigation observer.
- Do not add feature-driver helpers like `assertOnLoginPage()`, `assertIsOnAmountPage()`, `assertAuthStackCleared()`, or `assertAmountPageDoesNotExist()` when `AppDriver.assertIsOnPage()`, `assertPageExists()`, or `assertPageDoesNotExist()` already covers the assertion.
- Keep generated and edited test code formatter-friendly with a max line width of 120.

## Builders (`test/_core/test_setup/builders/`)

- Builders extend `BaseBuilder` and expose a fluent API for test data configuration.
- `build()` returns a `TestSetupConstructor` whose `setup()` wires data into the offline client and whose `tearDown()` resets all properties to `null`.
- Wire data through the **client provider pattern**: `getIt<IXxxClientProvider>().getClient() as OfflineXxxClient`.
- Builders do **not** call `fixture()`. Fixtures are loaded directly in test files when needed.

## Domain Tests (`test/domain/`)

- Pure Dart `test()` — no Flutter, no builders, no mocks.
- Value object tests are always allowed.
- Entity tests are allowed only when entity business logic is added/changed (computed properties, domain decisions, lookup/filter behavior).
- Do not add tests for use cases.

## Golden Tests (`test/presentation/`)

- Use `testGoldens()` from `golden_toolkit`.
- Golden tests must live under `test/presentation/<feature>/`.
- Page-level goldens use drivers with `goldenTest: true` and assert via `matchesGoldenFile()`.
- Each golden group covers light, dark, and accessibility variants.
